## THE DECISION — Option B, and exactly what it does and does not authorise

The operator was presented with two orderings for #243 and **chose Option B**.

**#243's issue file says it executes *before* #242 is enabled. That ordering is superseded.**
Do not follow the issue file on this point; follow this section.

### Why the ordering flipped

Verified against `schedule-closure-scheduler.service.ts:145` — `closeZone` selects
`dateTo < today AND liveScheduleFilter()`, i.e. only schedules still ACTIVE/OVERRIDDEN. Once a
schedule flips to PARTIAL it is **never selected again**. #242's recycler lives inside that method,
so **#242 can never reach the historical backlog.** It stops the bleeding from today forward; it
cannot heal history. #243 is therefore load-bearing, not housekeeping.

And the backlog **accrues ~300 rows every night** the closure cron runs without #242 (measured per
schedule date: 299, 126, 269, 294, 336, 301, 374, 369 …). Cleaning first therefore guarantees
cleaning twice. Option B cleans once, on a set that has stopped growing.

Checked for interaction, all three classes: C1 and C2 sit on already-closed schedules, and C3 tickets
have no live row, so **#242's sweep touches none of them in either ordering**. The stated purpose of
the original ordering — keeping `DEV_CLEANUP` out of #244's countable set — holds either way, because
#242 can only ever stamp `PLAN_EXPIRED` on schedules closing that night.

### The order of work

1. **Build #242** (`Status: ready-for-agent`, AFK — no further approval needed). Its issue file is
   accurate; only its "cleaned by #243 before this slice is enabled" aside is now wrong.
2. **Enable it** so the backlog stops growing.
3. **Then come back for #243** — with **freshly re-measured counts** — and ask for execution
   approval.

### What Option B does NOT authorise

**Option B is an ordering decision, not execution approval for #243.** #243 stays `Type: HITL` /
`ready-for-human`. Do not write the cleanup script into a runnable state, do not `pg_dump`, do not
execute. Its AC1 still requires explicit operator approval at execution time, and the counts move
nightly.

### The second, smaller call the operator settled

"Explicitly untouched: the 299 live rows on ACTIVE schedules" means **current work at execution
time**, not those specific 299 rows. Those exact rows aged from ACTIVE into PARTIAL overnight and are
now inside C2. The literal reading cannot satisfy V1 anyway (no live row on a non-live schedule).
