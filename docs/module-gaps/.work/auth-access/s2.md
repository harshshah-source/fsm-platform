## The two findings that matter

**1. Acting scope has no gate.** `acting-context.ts:29` grants `actedAsRole` to any CSM/OH that
sends `X-Acting-As-Zone` for any zone. It never asks whether that ZM is unavailable.
`role-backup.service.ts:64,77` (`isRoleUnavailable`, `currentActingRoleForZone`) — the cascade
resolution itself — has **zero callers** outside its own file. Its own header comment
(`acting-context.ts:20-22`) defers the authorization to "TB6+"; TB6+ never landed. Entry is a
`sessionStorage` write (`AuthProvider.tsx:135`) and the token carries no acting claim
(`auth.service.ts:54`), so exit is client-side only. P4, dangerous. → AA-01, H1, H5.

**2. Acting attribution is dropped on three different paths, inconsistently.** The seam is right:
`auditActor()` (`audit.service.ts:30`) is the single mapping and `withAudit` persists both columns
inside the mutation's transaction (`:60-73`). 24 files use it. But:
- 11 controller sites pass a literal `actedAsRole: null` (leave-request :69/:85/:103,
  intraday-updates :52/:94/:115, tickets :143, intraday-insertion :93, engineers :254,
  devices :131, cross-zone :113) — all manager write paths a CSM uses while acting.
- ~15 of 25 direct `tx.auditLog.create` rows omit the acting columns entirely, bypassing
  `auditActor()`: component-request (3), troubleshoot-submission (4), shadow-use (2),
  install-lifecycle (2), soft-state (1), bulk-unassign (1), verification (2 of 3). Verified at
  `troubleshoot-submission.service.ts:190` and `component-request.service.ts:203` — the `data`
  block carries `actorId`/`actorRole` and nothing else.
- `override.service.ts` (5/5) and `cross-zone-escalation`, `se-availability`, `install`,
  `auto-recovery` do carry it. So the same ledger holds both stamped and unstamped acting rows.

Consequence: `csmBackupShareByZone` filters `actingZone: { not: null }`
(`role-backup.service.ts:91`), so every unstamped acting action is invisible to the Operations
Head's CSM-backup-share report — the one control that would reveal routine ZM backup. P2 + O3.
→ AA-02, AA-03, H2, H3.

## Guard column — re-verified at source (conductor's correction #1)
| endpoint | scanner said | source says | judgement |
|---|---|---|---|
| `POST /api/auth/refresh` | none | `@Public()` on the **class**, `auth.controller.ts:17` | scanner misread; correctly role-agnostic — bearer is the refresh token itself |
| `POST /api/auth/logout` | none | same class-level `@Public()`, `:17` | scanner misread; correctly role-agnostic, and `auth.service.ts:44` deliberately no-ops so logout is not an oracle |
| `GET /api/me` | none | `@UseGuards(AuthGuard)` class-level, `me.controller.ts:11`, no `@Roles` | correct: every role reads its own session; `:25` returns `acted_as_role` |
None of the three is a scope hole. The `@Public` on login is expected — and is exactly why AA-04
(no throttler) bites: `@Public()` sits on the whole controller, so login, refresh and logout are all
unauthenticated and all unthrottled.
