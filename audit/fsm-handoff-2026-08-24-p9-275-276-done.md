## 5. Design decisions worth knowing before touching this code (not repeated in the progress reports' summaries above — read those for the full rationale)

- **`assignLane` (#275) does not reuse `assignTicket` by calling it.** A P2002 aborts the whole
  Postgres interactive transaction (#265's finding), so calling the single-ticket `assignTicket`
  (which opens its own transaction) from inside a shared per-lane transaction would defeat "one
  transaction per lane" on the first collision. `assignLane` rebuilds the same *logic* against a
  passed-in `tx`, using `FOR UPDATE ... SKIP LOCKED` immediately before each write instead of
  insert-then-catch.
- **Distribute's three strategies never re-derive eligibility.** `CandidateQueryService`'s
  `buildCandidateReadiness`/`applyHardFilters` (already the functions the recommender itself calls,
  since #274) is the one source of "who's eligible, at what tier, and passing right now" for all three
  strategies. `COVERAGE_TIER` calls the scoped engine (`runForZone` with the new `ticketIds`/
  `engineerIds` opts) directly; `CAPACITY_HEADROOM`/`PLANT_WHOLE` are allocation policy layered on the
  one shared read.
- **The console's draft `Lane` type gained `ticketOverrides?: Record<plantId, ticketIds>`** (#276) —
  additive, only populated when Distribute hands a lane a *partial* plant. A manually-built lane never
  sets it; the review screen (`openReview` in `AssignConsolePage.tsx`) falls back to resolving the
  whole plant via `GET /schedules/assignable-tickets` when no override exists, exactly as before #276.
  If you touch the ledger (`inDraft`) or a lane's `→ after / cap` figure, they now read the override
  when present — don't revert to summing whole-plant totals unconditionally, or a partial Distribute
  placement will silently over-report.
