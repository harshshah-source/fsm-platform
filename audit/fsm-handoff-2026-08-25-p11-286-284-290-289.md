## Judgement calls made against issue text — all recorded, none silent

Each is argued in its report; listed here so the next session knows they were deliberate:

- **#284 AC10 governs over the issue's prose.** The Required-change section says `?date=` defaults to

  exhaust a healthy zone; the contended case is bounded by the operating-day cutoff instead.

## Two things that deserve a decision, and are not one I could make

1. **A retention gap is now load-bearing.** #286 retires orphan recommendations rather than deleting
   them, so a crashed run's reasoning survives (that was the point). But `recommendations` and
   `dispatch_decision_traces` carry a documented 90-day retention that **nothing implements** — the
   only sweep is `partition-maintenance`, which owns telemetry partitions, the cron-claim table and
   the notification outbox, and touches neither. Those tables have always grown unbounded; this makes
   it matter. Argued in #286's report under "Not done here". **Worth filing an issue.**
2. **`reapStaleDispatchRuns`'s docblock was aspirational**, and is now true: it freed claims by the
   run-id list it had *just* aborted, so a reaper dying between its two writes left RUNNING claims no
   later pass could ever find. Fixed as part of #286. Mentioned because the same class of bug —
   a comment asserting a recovery path nothing exercises — is worth looking for elsewhere.

## One caution about method

The chip-split defect in #290 (two Remove buttons with the same accessible name) looked like a test
artefact and was not: the real fault was that two controls doing the identical thing to the identical
object claim a granularity the draft does not have. **When a test fails on something that looks
cosmetic, ask what the UI is asserting before you make the test pass.** The same applies to the
`Toast` type error — the fix was to narrow the type, not to invent the missing entry.
