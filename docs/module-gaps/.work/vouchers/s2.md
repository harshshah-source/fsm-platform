Backend is the strong half: 7 endpoints, all role-guarded, all four write verbs audited. The damage is
at the two ends the backend does not own — the mobile client, and the controls the code assumes rather
than enforces. Capability states and pointers are in `coverage.json`; this file is the argument.

## The four that matter

**C7 mandatory audited reason — settled 🟢, do not re-open.** `STATUS_NEEDS_REASON` returns
`REASON_REQUIRED` before any state read (`vouchers.service.ts:245`); the reason lands in `withAudit`
metadata (`:271`) and on the row (`:276`); admin UI blocks the same (`VoucherReviewPage.tsx:88`).
static.md's "0 write-verb endpoints with no audit write" is **confirmed at `file:line`** — exactly four
`withAudit` sites, all inline in the reached method, no helper hop: `:168` create, `:265` review,
`:291` resubmit, `:331` markPaid.

**C8 separation of duties — breached, by assumption not accident.** `REVIEW_ROLES`
(`vouchers.controller.ts:26`) includes `OPERATIONS_HEAD`; mark-paid (`:123`) is OH-only. `markPaid`
(`vouchers.service.ts:312`) checks `status !== 'APPROVED'` and never reads `reviewedBy` — which is on
the row (`schema.prisma:1182`) and free to check. The module's only self-dealing guard is
`actor.userId === voucher.seId` (`:252`), SE-only. Two-person control on cash rests on role names.
→ **VCH-02, P4, DANGEROUS.**

**C2 offline dedup — inverted, not missing.** Server is right: `findUnique` on
`seId_clientSubmissionId` (`:157`) over a real `@@unique` (`schema.prisma:1193`), returning the existing
voucher untouched. The client defeats it — `Crypto.randomUUID()` is called *inside* `handleSubmit`
(`VoucherFormScreen.tsx:81`), so every tap is a new key, and `submitting` clears in `finally` (`:88`) so
the button re-arms exactly on the timeout that prompts a retry. PRD:721-724 wants the id at draft time.
Duplicate payment, not a UX bug. → **VCH-01, P1, DANGEROUS.**

**C9 PAID reversal — one-way door, priced not accepted.** `VoucherStatus` (`schema.prisma:1142`) has no
reversal member; no un-pay route exists. Plausibly deliberate (Finance reverses outside the app), so
**VCH-08 carries `policyClause: P12` and `needsCall: true`.**

## What static reading found that the spine table did not

- **SPINE E-16 is marked `OK` in static.md:23 on route existence alone. It is not OK.** No client in
  `apps/mobile/src` or `apps/admin/src` calls `resubmit`; the grep returns prose and one unrelated
  troubleshoot test. `NEEDS_CLARIFICATION` is terminal in the shipped app — the ZM's most collaborative
  action is the one that strands the claim. Contradiction recorded, not averaged. → VCH-03.
- **The fraud control is fed nothing.** `activityCheck` (`:469`) proves only that a ticket id exists —
  no plant match, no date match, no assignment check (VCH-06). And the mobile form posts only
  `clientSubmissionId` + `items` (`:80`), so `ticketId`/`plantId` are always null and every row arrives
  as `NO_ACTIVITY_LINK`. The ZM sees the warning on 100% of rows and learns to ignore it. → VCH-05.
- **The Finance export is unaudited** (`controller.ts:108`). A GET emitting every SE name, zone and
  amount for a month, with no record of who pulled it. → VCH-09, P2.
- **Mark-PAID is a per-voucher loop, one tx each** (`:321`/`:331`, matching static.md's `tx = no`). A
  mid-batch failure leaves a half-paid batch under one `batchRef` and no reconciliation to find it.
  → VCH-10.
- **The notifier is a log line.** `LoggingVoucherNotifier` (`voucher-notifier.ts:31`) is the only
  implementation and `vouchers.module.ts:18` binds it unconditionally, while `VoucherReviewPage.tsx:228`
  tells the ZM "the SE is notified". The seam is legitimate under CLAUDE.md (push/WhatsApp is external);
  the claim on the screen is not. → VCH-07, C3.
