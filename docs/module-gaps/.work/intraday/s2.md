only gateway bound in the repo is `LoggingChannelGateway` (`notifications.module.ts:18`), which returns

notify IS the entire hand-off; there is no accept step left to catch the miss. **C2 = BROKEN** (INTRA-G1).

## is the §21 retirement clean? — no, three-quarters clean

Clean: `accept`/`decline`/`sweep-timeouts` gone; `MeIntradayInsertionsController` gone; mobile pins the 404s
as a regression test (`mobile/src/api/client.ts:423`, `client.test.ts:767`); admin labels only the two live
statuses; escalation semantics rewritten with reasons in place.

Not clean — `OBSOLETE` residue, all cheap:
- `schema.prisma:511-519` docstring still describes the offer state machine as the current lifecycle and
  cites CONTEXT §16 — the section §21 superseded. The schema is the durable artifact; this misleads next.
- `enum IntradayInsertionStatus` keeps `PENDING_ACCEPTANCE` / `DECLINED` / `TIMED_OUT`, and
  `status` still **defaults to PENDING_ACCEPTANCE** (`:548`) — a default no writer uses and no reader labels.
- dead columns still on every row: `declineReasonCode`, `retryCount`, `retryChain`, `whatsappSentAt`;
  `acceptanceDeadline: now` is written meaninglessly on the direct-assign path (`service:~318`).
- `manualAssign` writes `status: 'ACCEPTED'` (`service:445`) — offer vocabulary for a direct act — and the
  admin table maps only 2 of 6 statuses, so the ZM's own resolution renders as the bare word `ACCEPTED`
  with no tone (`IntradayQueuePage.tsx:74-77,105`).
- `/intraday-updates/add|remove|reorder` (`scheduling/intraday-updates.controller.ts:40,75,99`) have zero
  callers in admin or mobile; the ZM's real same-day edit goes through `POST /batches/:id/override`.

None of this is a §21 policy gap. It is deletion and relabelling work left undone — file as OBSOLETE, price low.
