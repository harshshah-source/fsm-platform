## the one that matters

`uptimePct()` returns **100** on `window <= 0` — `reports.service.ts:703`. Fleet Uptime reads only
`device_downtime_summary_monthly` (`:313`), the controller defaults to the **current** month
(`reports.controller.ts:117`), and cron writes only `previousUtcMonthStart`
(`business-sweep-scheduler.service.ts:124,262`) — so the month the hero KPI asks for is the one month
cron never computes. Empty cube → `0/0` → **100%** → `ReportsPage.tsx:107` paints it green with tone
`'success'` against a contractual 98% target, and the 6-month trend fan-out (`api/reports.ts:63`)
repeats it per un-aggregated month. If the job silently stops the number does not go stale, it goes
**perfect**. RPT-01, S3, DANGEROUS. Same month offset hits Root Cause (`:389`) and ZM Scorecard
(`:439`), but those degrade to honest zeros, so RPT-02 is S3 without the flag. System Efficiency
defaults to **today** (`:730`) while its cron finalises yesterday (`:257`).

## joins to the ingestion survey

Two independent staleness clocks; only the first is stamped. Ingestion owns telemetry freshness,
surfaced by `SnapshotBanner` (`SnapshotBanner.tsx:8`). This module adds a **second** clock nothing
displays — cube recompute (`business-sweep-scheduler.service.ts:257,262,267,272`). A green ingestion
banner is therefore not evidence a report number is current: it can be minutes fresh while Fleet
Uptime is served from a month-old cube, or no cube at all (RPT-01). RPT-03 prices the report-side
stamp only; the ingestion-side fix is not priced here and neither substitutes for the other.
