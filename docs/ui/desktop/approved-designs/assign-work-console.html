The manual assign screen never tells you what is left

Seven surfaces can move work to an engineer today. Not one of them shows how much work there is, how much remains after you press the button, or whether the engineer you picked can carry it. Here is what is actually built, why the shape is wrong, and one console that replaces it.

Scope Admin web · manual assignment & reassignment Branch feat/autoplant-integration Date 20 Aug 2026 Status Proposal — nothing implemented

The ask

Three things a dispatcher asked for

A complete view while reassigning — how many devices are left. Assigning many devices at once. And putting two or more engineers onto more than one plant in a single pass.

All three describe the same missing thing: the operator is working on a plan, and the software only understands one write at a time. Every manual path in the codebase is shaped N → 1 — many tickets, one engineer, committed immediately, no preview, no residual. The dispatcher's real job is M → N and it has no home.

The tell

The v2 reference puts Assign SE in the top bar as the one red primary button on every screen — it is meant to be the console. In code it navigates to the dashboard. The most prominent control in the product opens nothing.

Analysis

Three blind spots, all with the data already sitting there

1 · How much work am I about to hand over?

DeviceFilterOptions.plants carries {plantId, name, companyId} and nothing else. The operator ticks plants blind and learns the volume afterwards, from a toast. The number exists — PlantAssignSummary.perPlant[].openUnassigned — but it is computed during the write, inside the loop, so it can only ever be reported after the fact.

2 · How much is left?

Nothing anywhere answers it. plantDeviceStats in dispatch-transparency-query.service.ts:496 computes assignedDevices / unassignedDevices per plant, but it is wired only into dispatch transparency and never into an assignment flow.

Predicate mismatch — fix before reusing

plantDeviceStats counts tickets by assignment_state with no status filter. assignPlants writes only where status='OPEN' AND assignment_state='UNASSIGNED' and the ticket is not deferred (override.service.ts:466-471). Showing the first number beside a button that does the second would over-report what the button does. The console needs one shared predicate, not two.

3 · Can this engineer take it?

dailyCapacity is already on EngineerListRow and ZoneEngineer, and is rendered in exactly zero places. Coverage is shown as the engineer's global coverageType — which for a multi-plant engineer says nothing about whether they cover these plants. The per-pair answer lives in se_coverage.coverage_type, and the ordered eligibility list is one existing function, orderedCandidatesForPlant, that no admin surface can reach.

Analysis

The shape is wrong, not the styling

To put two engineers across three plants today, the operator runs AssignSePanel twice. Between the two runs the panel keeps no memory: the plant list looks identical, still carries no counts, and gives no sign that the first three plants are now spoken for. There is no basket, no diff, and no answer to "what will this day look like when I press go".

assignPlants loops assignTicket ticket by ticket with no enclosing transaction and no dry run. A partial failure leaves a partial plan behind a single aggregate toast. The one honest thing the current panel does — skipping tickets another manager deliberately deferred — exists as a code comment, never as UI.

What the redesign must not break

Q2 — capacity is a scheduler constraint, not an authorization limit. Over-capacity engineers stay selectable, visibly marked. No block, no forced confirm.
Q1 — dedicated → multi-plant → floating precedence is inviolable for the system. A human may cross it, but must see the tier they are crossing.
Q6 — no live GPS in Phase 1. No map, no ETA, no route line.
#269 owns the {committed, dailyCapacity} payload. This console consumes it; it does not define a second counter.

The redesign

One console: work pool, draft plan, candidates

Full-viewport, three columns, one running ledger, one commit. The top-bar Assign SE button finally opens it. Nothing is written until the operator commits, which is what makes the residual count live rather than retrospective.

The redesign

How the three asks are answered

  1. Complete view, before the write

    Every plant row carries open unassigned / total devices, its critical+ count, and the oldest silent age. The header ledger holds open · in draft · left after commit. Because nothing commits until the operator says so, "left" is a live number rather than a post-hoc report.

  2. Many devices at once

    Selection works at company, plant, or device level. A plant tick means "every open unassigned device here"; expanding it lets the operator peel off individual devices — the split SPLIT_BATCH already supports, but only inside one existing batch.

  3. Two or more engineers across more than one plant

    The draft plan is a set of lanes, one per engineer, each holding chips from any number of plants. Select several plants and several engineers, then Distribute proposes a split — by capacity headroom, by coverage tier, or keeping each plant whole — into the draft, where it stays editable.

  4. Whether the engineer can take it

    Coverage is shown per engineer-and-plant, so a lane spanning two plants shows two badges when they differ. Load reads 5 → 9 / 12: committed today, after this draft, against capacity. The candidate column is orderedCandidatesForPlant rendered honestly — tier-grouped, including the engineers the hard filters dropped and the reason why.

  5. A commit that survives partial failure

    One review diff, one mandatory reason, then a transaction per engineer. The result reports per engineer rather than as one aggregate toast, so a lane that fails is legible and re-runnable while the rest stand.

The redesign

The commit review

The last screen before anything is written. It is a diff, not a confirmation dialog: it states what changes, what it costs, and what is still unassigned afterwards.

Build

What the backend has to expose

Mostly exposure of functions that already exist and already have tests. Nothing here is a new algorithm.

Reads

  • GET /schedules/assignable-work?zone&date — company → plant → device tree with {openUnassigned, totalDevices, criticalCount, oldestInactivityHours, heldCount}, built on the same predicate assignPlants uses, so the number on screen is the number the button will move.
  • GET /schedules/candidates?plantIds[] — per plant, orderedCandidatesForPlant joined to applyHardFilters and to #269's {committed, dailyCapacity}: tier, verdict, drop reason, availability and kit state per engineer.

Write

  • POST /schedules/assign-batch — {reasonCode, lanes:[{seId, ticketIds[]}]}, one transaction per engineer, one result row per engineer. assignPlants survives as the plant-shorthand that expands into lanes, so the Device Detail panel keeps working unchanged.
  • A dry run of the same body, reusing the dryRun seam #250 already built into the recommender, so Distribute proposes from the real selection logic rather than a second copy of it in the client.

Repairs on the way past

  • available-ses returns bare UUIDs. Give it the candidate row shape above and the missing intra-day manual-assign modal becomes buildable.
  • PlannerPage renders engineerId where reference 16 shows a name, and omits the LOAD / CAP column the reference specifies. Both values are already in ZoneEngineer.
  • CriticalQueue.tsx is orphaned but already contains an engineer picker, one-click assign and the deferral confirm. Absorb it as the console's Critical+ preset instead of leaving it dead or rebuilding it.

Sequencing

The console cannot land before the numbers it displays are true.

Must land firstWhy
#178Closure never clears assignment — until it does, committedDayLoad overcounts and the load column lies.
#269Defines the one {committed, dailyCapacity} payload. A second counter here would fork the definition.
#266Score currently decides nothing — chosen = planner ?? passed[0]. Showing a candidate order the engine does not actually use would teach the operator a false model.
#262Per-SE dispatch transactions — the natural home for assign-batch's per-lane transaction shape. Built separately, the two produce competing transaction strategies over the same tables.

#269's text says "existing pages, no redesign", and that is right: #269 is the instrumentation, this is the surface it makes possible. They are not in competition — this proposal is the consumer #269 was written for.

Open

Three calls that are not mine to make

  • Does the console replace the Device Detail panel, or sit beside it? Keeping both means two answers to "how do I assign", which is how we reached seven surfaces. Recommendation: the panel stays as a shortcut that deep-links into the console, pre-scoped to that device's plant.
  • Is a draft persistent? A shared, resumable draft is more useful and considerably more work — its own table, an owner, and a staleness rule for when the underlying tickets move. Recommendation: session-local for v1, said plainly on screen.
  • Does the Zonal Manager get Distribute, or only Operations Head and Central Service? The RBAC ladder already splits preview and holds (all managers) from dispatch-run (OH + CSM). Distribute is closer to a dispatch run than to a single assignment.
