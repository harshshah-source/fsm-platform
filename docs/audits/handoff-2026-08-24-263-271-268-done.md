**`docs/SYSTEM-STATE-2026-07.md` is the recurring trap.** It is CRLF-native and shared-dirty with that
other session's edits interleaved with whichever session last updated it. The partial-staging recipe
(save combined → `git checkout --` to clean HEAD → reapply only your own hunk via a script → stage →
restore the combined content to the worktree, byte-for-byte, LF-normalized before any Python write)
is now used identically three times this session (#263, #271, #268) — grep this session's own
`git log -p` on that path for the exact scripts if you need the pattern again, or just replicate the
same five steps. **Watch for one specific footgun:** `io.open(path, 'w', encoding='utf-8')` with no
`newline=''`/`newline='\n'` argument silently converts the whole file to CRLF on Windows Python, which
then makes `git diff` misleadingly look small (git's `core.autocrlf` normalizes it away) while the
actual working-tree bytes have flipped every line ending. Always pass `newline='\n'` (or `'\r\n'` if
matching a file confirmed CRLF-native via `git show HEAD:<path> | python -c "count \r\n vs \n"`) —
never omit it.

**Two other files also turned out CRLF-native and got the same fix applied when this session
accidentally flipped them:** `CONTEXT.md` and the `.scratch/fsm-platform-v1/issues/268-*.md` issue
file. Both are back to correct LF now (verified via the same check). Re-verify with the same one-line
`crlf`/`lf-only` count before trusting a "clean diff" on any file you edit via a Python script this
session touched, in case the same mistake recurs.
