### Activation checklist (env/ops enable order — do NOT flip casually)

The schedulers are OFF by default. When activating for real (a deliberate ops step, post zone
ratification), enable in this order and mind the couplings:

1. **`eligibility_mode`** (audited `system_settings`, OH-owned) — `pgi` (canonical) requires a live SAP
   PGI feed; until then the interim `all-deployed` proxy makes current-fitment-on-ACTIVE devices eligible.
   Harmless to set while schedulers are OFF (it only bites on the next pipeline recompute).
2. **`INGESTION_SCHEDULER_ENABLED=true`** — turns the pipeline self-running (masters daily + telemetry
   every 30 min). **MUST be enabled together with `PARTITION_MAINTENANCE_ENABLED=true`** — without it,
   after the 3-day partition create-ahead runway new pings silently fall into the DEFAULT partition and
   retention never runs (handoff §4 item 5 / `docs/archive/HANDOFF-autoplant-ingestion-2026-07-07.md`). Treat the
   two as one switch. Also set `INGESTION_STALE_RUN_MIN` above the telemetry cadence (reaper safety).
3. **`BUSINESS_SWEEPS_ENABLED=true`** — turns on dispatch (`business-dispatch` cron) + the 10 field-loop
   sweeps (verification / intraday-timeout / cross-zone / install-verification / …). Needs SE + coverage
   data present (else every ticket is UNASSIGNABLE) — SEs are admin-entered via `/engineers/manage`.
   **SECOND SWITCH PAIR — sweeps depend on ingestion (#148, 2026-07-22).** The verification and
   install-activation sweeps resolve a 24-hour window against `raw_device_snapshots`, so they are only
   meaningful while step 2 is actually running. **This pair is now ENFORCED IN CODE**, not just
   documented: both sweeps refuse to expire a window until the telemetry watermark
   (`snapshot_runs.data_as_of`) has advanced past the submission / activation
   (`VerificationService.windowExpired`, `InstallLifecycleService.activationWindowExpired`). Before
   #148 a submission made while ingestion was paused aged into an **irreversible**
   `FAILED_VERIFICATION` / `FAILED_ACTIVATION` — rolling back `PRE_VERIFICATION` inventory and pushing
   a false failure to the SE — regardless of whether the SE had fixed the device.
   **Consequence to watch:** the guard converts a wrong verdict into a window that stays PENDING
   indefinitely while telemetry is frozen. That is the correct trade (it can only ever delay a failure,
   never cause one), but it must be **visible** — surfacing stalled windows on `/build-health` is
   #148 slice 3, still open. **Never** "fix" a stalled window by auto-expiring after a grace period;
   that re-creates the original bug with a longer fuse.

> on while step 2 is off**, exactly the inversion the pairing above warns about. That is what made
> #148 an armed defect rather than a hypothetical one, and it is why the pairing is now enforced in

Manual HTTP triggers (`POST /api/integration/run-pipeline`, `POST /api/schedules/dispatch-run`, the

runs while the flags stay OFF.
